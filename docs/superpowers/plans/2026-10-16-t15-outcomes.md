# T15 Daily and Weekly Outcomes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execution method is pending owner selection; native execution is recommended. Read the spec before implementing.

**Goal:** Show separate daily/weekly usage, exercise activity and awarded-time outcomes, with durable coverage and evidence-based comparison eligibility.

**Architecture:** Extend the existing transactional history snapshot with coverage intervals and activity modes. Record coverage independently of spending, through the serialized production monitor. Pure Kotlin aggregates outcomes and determines comparison eligibility; Compose renders those results.

**Tech Stack:** Kotlin/JVM, JUnit 4, Compose Material 3, Room, DataStore; existing verification scripts.

**Spec:** `docs/superpowers/specs/2026-10-16-t15-outcomes-design.md` — approved by the owner on 2026-10-16.

**Plan status:** Native execution selected by the owner's “do tasks” request. Implementation and focused JVM regression sources are prepared; no Gradle test, instrumentation test, emulator or device run was performed per the owner's explicit constraint. Build/schema and phone verification remain pending.

## Global Constraints

- T15 only; T16 integrated delivery and physical-device acceptance stay separate.
- Preserve the shared checkout, index and unrelated existing changes; no commits,
  staging, publication or installation during this planning task.
- Reuse Kotlin/JVM, Compose Material 3, Room and DataStore; add no dependency,
  permission, foreground service, wake lock, analytics or network requirement.
- Support Persian RTL, English and French with locale-aware durations, accessible
  headings/controls, mixed-number direction and non-color-only coverage labels.
- Integer milliseconds for durations; ISO local dates for stored day identity.
- Missing or hidden monitoring data must never imply zero usage or improvement.
- Keep enforcement counters, award identities and captured challenge terms intact.
- Coverage checkpoints: 60,000 ms idle delay; 90,000 ms maximum confirmation gap;
  permitted wall/monotonic drift at most 2,000 ms. Do not change the budget
  controller's existing 5,000 ms maximum spending observation gap.
- Preserve the owner's shared checkout and index during execution as well. Do
  not commit automatically; report suggested commit boundaries after each task.

## Review Focus

1. A late write after history deletion or restart must stay hidden for the
   deleted day; Task 1 tests cutoff enforcement and Task 3 tests Room reopen.
2. Coverage success after a suspended observation has been invalidated must not
   certify that interval; Tasks 2 and 4 test generation invalidation.
3. A missing usage row can mean zero only with complete matching coverage and
   consistent visible accounting; Task 5 tests unknown, zero and inconsistent data.
4. DST, midnight and a change of zone or selected targets must not produce a
   comparison between different observation scopes; Tasks 2 and 5 test them.
5. Exercise-only activity, removed apps and awarded versus consumed credit must
   remain distinct and appear exactly once; Task 5 pins all three in one fixture.
