## Two phases for every task

1. **Implementation:** make the scoped change, write relevant regression tests/fixtures, review source, and prepare QA handoff. **Do not run Gradle commands, builds, Gradle lint, emulator tests, instrumentation, or physical-device acceptance in this phase.** Source/document checks are allowed. Implementation can finish with tests written but unrun; label it `IMPLEMENTED — QA NOT RUN`.
2. **QA:** run the task's automated and/or device/manual scenarios, record actual results, and decide acceptance. Gradle and emulator/device checks belong here. For qualification/performance tasks, implementation prepares the harness and matrix; QA performs the measurements. A required unrun/blocked case prevents task acceptance.

Statuses are independent: implementation `NOT STARTED / IN PROGRESS / IMPLEMENTED`; QA `NOT RUN / IN PROGRESS / PASS / FAIL / BLOCKED`. `GATED` means the task's entry condition is unmet, not implementation complete. An implementation handoff is not QA PASS. A QA-discovered fix returns to Implementation, then gets a new QA run.

Generating this package does not execute the backlog, change existing authorization, grant device permissions, or turn optional proposals into shipped features. The owner requested specifications, plans and scenarios. All newly defined scenarios start **NOT RUN**, even when related historical tests exist.

## Delivery order and gates

1. Restore evidence: I01, I02, initial I10 inventory. Full suites must be unfiltered; native process death is a failed run, not proof remaining cases passed.
2. Stabilize monitoring: I05 → I06 → I07 → I09, with I08 alongside. Follow with F-A. Keep accounting authority in `BudgetEngine`.
3. Qualify current experience: I11 baseline can run alongside I04; I03 accepts the full loop only after its dependencies pass. I04 and I11 share evidence without depending on each other's acceptance. Refresh I10 with the exact tested source/artifact identity.
4. Run P01 after the baseline gates. Consider F-B after setup acceptance. F-C/F-D follow demonstrated usefulness; F-E/F-F/F-G remain demand-gated. I12 and M01/M02 are conditional improvements, not reasons to delay correction of P0 failures.

M01/M02, if undertaken after qualification, invalidate affected navigation/lifecycle evidence until regression QA passes. Optional feature delivery also reruns affected baseline cases; an older release gate does not qualify changed code automatically.
